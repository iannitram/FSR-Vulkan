# Licences for each vendor path

Status: **checked 2026-11-12** (roadmap item 5.01, issue #16). This is a factual reading of the vendors' published terms, not legal advice. Where a clause is ambiguous the table says so and gives the safe reading. Whatever the terms allow, we ship nothing of NVIDIA's, Intel's or AMD's beyond the MIT sources upstream vendors (SPEC Won'ts, ADR 0001); the "what we may ship" column says what the terms would permit, not what we do.

## Questions 5.01 answers

**1. May a game redistribute `nvngx_dlss` and Intel's XeSS library beside its executable?**

- **DLSS: yes, the game may, on conditions.** The licence grants "Distribute any software and materials within the SDK, other than developer tools provided for your internal use, as incorporated in object code format into a software application" (Sec. 1.c). Conditions: "An application must have material additional functionality, beyond the included portions of the SDK" (2.a); the game must "distribute the SDK subject to the terms at least as protective as the terms of this license" (2.c); and "you may not distribute or sublicense the SDK as a stand-alone product" (4.b). The licence text never names `nvngx_dlss`; the SDK's `lib/` folder carries it (`nvngx_dlss.dll` on Windows, `libnvidia-ngx-dlss.so.*` on Linux), and it is "within the SDK" and not a developer tool. Redistribution is therefore the game's right under its own acceptance of the licence. We are a library, not that application, and we do not hold a licence to redistribute it for them: another reason we ship none.
- **XeSS: yes.** "You may use and redistribute the software, which is provided in binary form only ... without modification, provided the following conditions are met" (Use and Redistribution). The v3.0.2 SDK ships `libxess.dll`; the developer guide says it "must be placed next to the executable or in the DLL search path". The runtime is not otherwise on a non-Intel player's machine: the guide says the dispatcher loads "the XeSS-SR runtime shipped with the game, the version provided with the Intel Graphics driver, or the cross-vendor implementation", and only Intel's driver bundles one. On an NVIDIA or AMD machine the game must ship `libxess.dll`.

**2. May an MIT library load them at run time?**

- **Yes for both, with one build-time caveat for DLSS.** Neither licence restricts what code loads the runtime; both restrict copying and altering the SDK. Loading with `dlopen` / `LoadLibrary` copies nothing of theirs into our tree or packages.
- **DLSS ambiguity.** Sec. 4.e: "You may not use the SDK in any manner that would cause it to become subject to an open source software license." Safe reading: loading NVIDIA's file from the player's machine does not make it subject to MIT, because we never distribute it, so it applies only if we bundle or statically link SDK files into our MIT package. We do neither.
- **DLSS headers and import library are not free to copy.** `nvsdk_ngx_vk.h` carries `SPDX-License-Identifier: LicenseRef-NvidiaProprietary` and "Any use, reproduction, disclosure or distribution of this material ... without an express license agreement ... is strictly prohibited". The licence lets us distribute SDK materials only "in object code format" (1.c), so the DLSS headers and `libnvsdk_ngx.a` cannot be committed to this repo or installed by our package. A DLSS backend has to be built against an SDK the builder has downloaded and accepted the licence for. Raised on issue #16 for 5.07.
- **DLSS GPU limit.** The SDK is "licensed for you to develop applications only for their use in systems with NVIDIA GPUs" (Supplement Sec. 1): the DLSS backend must be chosen only on an NVIDIA GPU, as M7 already says.
- **XeSS:** the headers are MIT (`xess_vk.h`: `SPDX-License-Identifier: MIT`; `inc/MIT.txt`), so they may be vendored with Intel's copyright line. I opened `xess_vk.h` and `MIT.txt`, not every header.

**3. What attribution does each require?**

- **DLSS (the game's duties):** "you must attribute the use of the applicable SDK and include the NVIDIA Marks on splash screens, in the about box of the application (if present), and in credits for game applications" (Supplement 7.1(b)); "You are required to notify NVIDIA prior to commercial release of an application" that incorporates the DLSS SDK, at https://developer.nvidia.com/sw-notification (Supplement Sec. 4); and "you may not indicate that an application created with the SDK is sponsored or endorsed by NVIDIA" (4.c). The notice line "This software contains source code provided by NVIDIA Corporation." applies only to modified or derivative source of the SDK that is distributed (2.b), which we do not do. Ambiguity: the licence does not say whether a game that loads a driver-supplied DLSS runtime, and ships none, "incorporates" the SDK; the safe reading is that any game built against the SDK does, so the game does the notification and credits whether or not it ships the file. Our `integration.md` (6.01) should tell game developers this.
- **XeSS:** "Redistributions must reproduce the above copyright notice and these terms of use in the Software and in the documentation and/or other materials provided with the distribution"; "Neither the name of Intel nor the names of its suppliers may be used to endorse or promote products derived from this Software without specific prior written permission." Ship `LICENSE.txt` and the third-party file (`third-party-programs.txt`) with `libxess.dll`.
- **FSR 4 / AMD binaries:** "Redistributions must reproduce the above copyright notice, this permission notice, and the following disclaimers and notices in the Software documentation and/or other materials provided with the Software."
- **Us:** a one-line pointer in `NOTICE.md`-style credits that each vendor path loads a vendor runtime, once a backend lands. The vendors' notices travel with the files the game ships.

**4. Does XeSS have a Linux Vulkan runtime?**

- **No, not that Intel publishes.** The SDK repository (`bin/`, `lib/`) and the v3.0.2 release contain only Windows files (`libxess.dll`, `libxess.lib`, `.exe` samples); the developer guide's requirements start with "Windows 10/11 x64". I found no Linux or macOS runtime in the repository, its release list or its documentation. The Vulkan path exists (`xess_vk.h`, `basic_sample_super_resolution_vk.exe`) but only as a Windows DLL. So 5.04 and 5.05 are Windows only; on Linux and Mac the XeSS backend reports "no runtime" and falls back to FSR 3. The Linux build still probes for `libxess.so` and `libxess.so.1` (`universal/src/uscale_caps.c`), through the normal loader search and not the folder beside the executable, so a future Intel Linux runtime is picked up without a code change. Today the probe finds nothing and the backend falls back to FSR 3. If Intel adds a Linux build later, the licence text already covers it ("the software, which is provided in binary form only").

**5. What terms cover AMD's FSR 4 asset files?**

- **AMD's own FSR 4 files (the signed binaries):** the FidelityFX SDK's `docs/license.md` opens "The following license applies to all files except as noted below", grants distribution "in binary form only", and states "No reverse engineering, decompilation, or disassembly of this Software is permitted." The same file lists `Kits\FidelityFX\signedbin\amd_fidelityfx_upscaler_vk.dll` (and the other signed DLLs) among "These source files ... subject to the following license", followed by an MIT text. Ambiguity: the list says "source files" but names DLLs, and our `UPSTREAM.md` read the 2.3 licence as stricter for signed binaries. Safe reading: treat the signed DLLs as binary-only, unmodified, with AMD's notice reproduced. A game may redistribute them under either reading.
- **How FSR 4 is delivered:** AMD's FSR 4 manual says it "requires integration using the FidelityFX API and use of the signed binary distribution" and points to the "PrebuiltSignedDll" folder. The page itself names no DLL, version, Linux binary, or model or weight file; the DLL names (`amd_fidelityfx_upscaler_vk.dll` for Vulkan) come from the SDK repository's `Kits/FidelityFX/signedbin/` listing at v2.4.0, which holds only Windows `.dll` and `.lib` files. I found no Linux binary from AMD.
- **The v07 asset files our provider loads are not in any AMD package I could find.** Upstream's `ffxFsr4V07BuildAssetSet` names `fsr4_model_v07_i8_*_pre.spv`, `*_pass<N>.spv`, `*_post.spv`, `*_initializers.bin` and `*_pre_weights.bin`. Searching AMD's FidelityFX SDK repository tree (commit `7539ae8b`) and the web found no AMD page or release that publishes files with those names or states terms for them, and the SDK repository carries no licence for them. Upstream's own `README.md` says "obtain them under their applicable terms", which names no source. So, for those files, the terms are unknown, and the safe reading is that no licence is granted until AMD says so. SPEC risk "AMD's FSR 4 source and models carry no licence file" still stands for them. This does not stop us, since we ship none (owner ruling 2026-11-02) and the game supplies them, but it means a game cannot get them "from AMD's download" unless AMD's signed distribution is what the game uses. Raised on issue #16 for 5.03.
